Пошук змінних: Спочатку параметри та локальні змінні → потім поля структури. Локальна змінна «ховає» (hides) одноіменне поле.

Перший параметр цієї функції — вказівник на об'єкт (this).

Реалізувати правило мутабельності (The Mutation Rule):
Функція вважається mutating, якщо вона:
Робить присвоєння своєму полю (x := ...).
Викликає іншу mutating функцію на своєму об'єкті або на своєму полі.
Алгоритм обчислення: Через можливі циклічні виклики методів (A→B→A) мутабельність обчислюється після перевірки всіх тіл функцій: спочатку позначаються ті, де є пряме присвоєння полян, а далі запускається цикл розповсюдження прапорця (fixed-point iteration), поки нові функції перестануть позначатися як mutating.

2. Порівняння двох варіантів побудови (Architectural Approaches)
Вимоги пропонують вибір між двома підходами до реалізації в компіляторі.
Варіант 1: New nodes all the way (Класичний / AST-Native)
Нові вузли MemberFn та MemberCall залишаються в AST-дереві на всіх етапах.
Семантичний аналіз (Sema): Пишеться окремий метод analyze_member_call та analyze_member_fn. Sema знає про поля структури і обробляє доступ до них прямо під час обходу AST.
Генерація коду (CodeGen): Додається окремий метод codegen_member_call, який сам генерує GEP для this, та codegen_member_fn, який генерує сигнатуру з першим аргументом-вказівником.
Переваги:
Точний зв'язок з вихідним кодом: AST дзеркально відображає те, що написав користувач. Повідомлення про помилки (line:column) генерувати набагато простіше й точніше.
Прозорість аналізу: Під час семантичного аналізу легко перевіряти типи, доступність та розраховувати прапорець mutating без маніпулювання додатковими аргументами.
Гнучкість у генерації коду: Можна точно контролювати ABI передачі this (наприклад, позначати sret, nonnull, dereferenceable у LLVM).
Мінуси:
Потрібно розширювати кожен прохід (Pass) компілятора. Якщо у вас є Sema, TypeChecker, Optimizer, CodeGen, Linter — у кожен із них треба додати нові класи/методи для MemberFn та MemberCall.
Більше дублювання коду в CodeGen (локальна змінна шукається так, а поле через this — інакше).
Варіант 2: Rewrite after parsing (Децукоризація / AST Lowering)
Одразу після парсингу AST «переписується» (Rewritten/Lowered) у базові конструкції мови:
struct Point { fn shift... } перетворюється на звичайну глобальну функцію Point_shift(Point* this, i32 dx).
Будь-яке поле x всередині методу замінюється на вузол this.x.
Виклик p.shift(2) замінюється на виклик звичайної функції Point_shift(&p, 2).
Переваги:
Простота CodeGen: Генератор коду взагалі не знає про існування методів! Він просто генерує звичайні функції та їх виклики.
Мінімум нового коду: Не потрібно додавати складну логіку генерації вказівників в IR для нових вузлів, бо ви перевикористовуєте механізм звичайних викликів функцій.
Мінуси:
Складність повідомлень про помилки: Якщо в згенерованому коді виникає помилка (наприклад, помилка типів або мутабельності), користувачеві важко вивести зрозуміле повідомлення, бо в AST вже немає оригінального p.shift(2), а є Point_shift(&p, 2).
Захист від колізій імен: Потрібно розробляти систему манглінгу імен (Name Mangling), щоб створена функція Point_shift випадково не перекрила реальну функцію користувача fn Point_shift(), яку він сам міг написати в коді.
Необхідність службових метаданих: Компілятор все одно має пам'ятати, що перший аргумент this треба передавати за адресою, навіть якщо мова за замовчуванням передає структури за значенням (by-value).

Крок 1: Обчислення типу та перевірка мутабельності ланцюжка (check_lvalue_mutability)
Створіть функцію, яка рекурсивно занурюється в ліву частину доступу і повертає true, тільки якщо весь ланцюжок до цієї точки є мутабельним.
Псевдокод (на мові Rust / C++ подібному системному коді):
// Повертає (Type, is_mut) для виразу доступу
fn check_path_mutability(expr: &Expr, env: &SymbolTable) -> (Type, bool) {
    match expr {
        // Базовий випадок: Змінна (наприклад, `c` або `p`)
        Expr::Variable(name) => {
            let symbol = env.lookup(name);
            let is_mut = symbol.is_mutable; // Чи була змінна оголошена як `mut`
            return (symbol.type, is_mut);
        }

        // Поле структури (наприклад, `c.center`)
        Expr::FieldAccess { target, field_name } => {
            // 1. Спочатку рекурсивно перевіряємо ліву частину (`c`)
            let (target_type, target_is_mut) = check_path_mutability(target, env);
            
            // 2. Шукаємо поле в структурі
            let struct_def = env.lookup_struct(&target_type);
            let field_info = struct_def.find_field(field_name);
            
            // 3. Ланцюжок є mut ТІЛЬКИ якщо і ліва частина mut, і сам запис поля mut!
            let path_is_mut = target_is_mut && field_info.is_mutable;
            
            return (field_info.type, path_is_mut);
        }

        _ => error("Expected variable or field access in member call"),
    }
}


Крок 2: Перевірка самого виклику методу (analyze_member_call)

            )
        );
    }

3. Як виявити, які методи є mutating (Fixed-Point Iteration)
Оскільки методи можуть викликати один одного циклами (наприклад, fn A викликає fn B, а fn B викликає fn A), ви не можете визначити мутабельність за один прохід AST.
Використовується алгоритм непорушної точки (Fixed-Point Iteration):
[ Крок 1: Прямі присвоєння ]
Пройти по тілу кожного методу у структурі.
Якщо метод містить `x := ...` (де `x` — поле структури):
    позначити method.is_mutating = true

[ Крок 2: Розповсюдження прапорця (Цикл) ]
repeat:
    changed = false
    for each struct in program:
        for each method in struct:
            if method.is_mutating == true:
                continue // Вже мутуючий, пропускаємо

            // Перевіряємо всі виклики методів всередині тіла цього методу
            for each call in method.body:
                if call is member_call on same object (or its field):
                    target_method = find_method(call)
                    if target_method.is_mutating:
                        method.is_mutating = true
                        changed = true
until changed == false


Важливі нюанси під час визначення is_mutating:
Локальні змінні «перекривають» поля: Якщо у методі написано i32 x{10}; x := 5;, і x є локальною змінною/параметром, це НЕ робить метод mutating. Метод мутуючий тільки тоді, коли відбувається присвоєння полю структури.
Присвоєння не-мутабельному полю: Якщо всередині методу робиться x := ..., але поле x оголошено без mut, аналізатор одразу видає помилку: an assignment to a const field inside a member function.

User prompt: Як згенерувати код для універсального виведення структури (print(c)), якщо тип структури відомий на етапі компіляції? Як автоматично пройтися по таблиці полів структури в LLVM IR, зробити gep для кожного поля, завантажити його значення та викликати відповідний формат (%d, %lld, %s, або рекурсивно вивести вкладену структуру)?
Response: Для автоматичної генерації коду універсального виводу (print(c)) у компіляторі, коли тип структури відомий на етапі компіляції, використовують підхід структурної рефлексії на етапі компіляції (Compile-time Type Reflection).
Оскільки низькорівневий LLVM IR сам по собі «не знає» назв полів і типів високого рівня, вся логіка генерації коду має відбуватися у вашому компіляторі (на етапі CodeGen) під час обходу AST/Таблиці типів, а не в самому LLVM IR.
Основний алгоритм генерації (CodeGen Strategy)
Коли генератор коду зустрічає виклик print(c), де c має тип Circle:
Отримати метадані типу: Компілятор бере з таблиці типів (Symbol Table / Type Registry) інформацію про структуру Circle: перелік її полів, їхні типи та порядок (індекси).
Створити рекурсивну функцію генерації: Компілятор генерує послідовність інструкцій GEP (GetElementPointer) + Load + Call print для кожного поля по черзі.
Оформити гарний вивід: Додати символи розделителів (наприклад, Circle { center: , , , }), щоб результат був читабельним.
Схема обходу полів у компіляторі (Псевдокод CodeGen)
Нижче наведено приклад того, як має виглядати метод generate_struct_print у вашому генераторі коду (на C++/Rust/Python, яким написано ваш компілятор):
fn generate_print_expr(builder: &mut IRBuilder, expr: &Expr, symbol_table: &SymbolTable) {
    let val_type = expr.get_type();

    match val_type {
        Type::I32 => {
            let val = generate_code(expr);
            builder.build_call(printf_func, &[string_fmt("%d"), val]);
        }
        Type::Struct(struct_name) => {
            // Отримуємо адресу структури в пам'яті (alloca або pointer)
            let struct_ptr = generate_lvalue_address(expr); 
            let struct_def = symbol_table.lookup_struct(&struct_name);

            // 1. Друкуємо назву структури та відкриваючу дужку
            builder.build_call(printf_func, &[string_fmt(&format!("{} {{ ", struct_name))]);

            // 2. Ітеруємося по всіх полях структури за їхніми індексами (0, 1, 2...)
            for (index, field) in struct_def.fields.iter().enumerate() {
                if index > 0 {
                    builder.build_call(printf_func, &[string_fmt(", ")]);
                }

                // Друкуємо назву поля
                builder.build_call(printf_func, &[string_fmt(&format!("{}: ", field.name))]);

                // 3. Обчислюємо адресу i-го поля за допомогою GEP
                // [0, index] -> 0 для розархівації вказівника, index для поля
                let field_ptr = builder.build_gep(
                    struct_def.llvm_type, 
                    struct_ptr, 
                    &[i32_const(0), i32_const(index)]
                );

                // 4. РЕКУРСІЯ: Якщо поле є базовим типом -> Load і printf
                //             Якщо поле є іншою структурою -> Рекурсивний виклик!
                if field.type.is_struct() {
                    // Передаємо field_ptr як адресу вкладеної структури
                    generate_print_struct_by_ptr(builder, field_ptr, &field.type, symbol_table);
                } else {
                    let field_val = builder.build_load(field.llvm_type, field_ptr);
                    generate_print_primitive(builder, field_val, &field.type);
                }
            }

            // 5. Друкуємо закриваючу дужку
            builder.build_call(printf_func, &[string_fmt(" }")]);
        }
    }
}


Приклад результату в LLVM IR
Якщо у вас є структури з вашого завдання:
struct Point { i32 mut x, i32 mut y }
struct Circle { Point center, i32 radius }


І ви викликаєте print(c) для об'єкта Circle c, ваш компілятор має згенерувати наступний LLVM IR:
; Строкові константи для форматування (оголошуються в глобальній області)
@str_circle_open = private unnamed_addr constant [11 x i8] c"Circle { \00"
@str_center_label = private unnamed_addr constant [10 x i8] c"center: \00"
@str_point_open = private unnamed_addr constant [10 x i8] c"Point { \00"
@str_x_label = private unnamed_addr constant [4 x i8] c"x: \00"
@str_fmt_i32 = private unnamed_addr constant [3 x i8] c"%d\00"
@str_comma = private unnamed_addr constant [3 x i8] c", \00"
@str_y_label = private unnamed_addr constant [4 x i8] c"y: \00"
@str_radius_label = private unnamed_addr constant [10 x i8] c"radius: \00"
@str_close_br = private unnamed_addr constant [4 x i8] c" }\00"

declare i32 @printf(i8*, ...)

define void @print_circle(%Circle* %c_ptr) {
entry:
  ; 1. Друк "Circle { "
  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([11 x i8], [11 x i8]* @str_circle_open, i32 0, i32 0))

  ; --- ПОЛЕ 0: center (Вкладена структура Point) ---
  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([10 x i8], [10 x i8]* @str_center_label, i32 0, i32 0))
  
  ; GEP для вкладеної структури (Index 0 в Circle): %Point* %center_ptr
  %center_ptr = getelementptr inbounds %Circle, %Circle* %c_ptr, i32 0, i32 0

  ; --- РЕКУРСИВНИЙ ВИВІД Point ---
  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([10 x i8], [10 x i8]* @str_point_open, i32 0, i32 0))
  
  ; Point.x (Index 0 в Point)
  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([4 x i8], [4 x i8]* @str_x_label, i32 0, i32 0))
  %x_ptr = getelementptr inbounds %Point, %Point* %center_ptr, i32 0, i32 0
  %x_val = load i32, i32* %x_ptr
  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([3 x i8], [3 x i8]* @str_fmt_i32, i32 0, i32 0), i32 %x_val)
  
  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([3 x i8], [3 x i8]* @str_comma, i32 0, i32 0))

  ; Point.y (Index 1 в Point)
  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([4 x i8], [4 x i8]* @str_y_label, i32 0, i32 0))
  %y_ptr = getelementptr inbounds %Point, %Point* %center_ptr, i32 0, i32 1
  %y_val = load i32, i32* %y_ptr
  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([3 x i8], [3 x i8]* @str_fmt_i32, i32 0, i32 0), i32 %y_val)

  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([4 x i8], [4 x i8]* @str_close_br, i32 0, i32 0))
  ; --- КІНЕЦЬ Point ---

  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([3 x i8], [3 x i8]* @str_comma, i32 0, i32 0))

  ; --- ПОЛЕ 1: radius (i32) ---
  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([10 x i8], [10 x i8]* @str_radius_label, i32 0, i32 0))
  %radius_ptr = getelementptr inbounds %Circle, %Circle* %c_ptr, i32 0, i32 1
  %radius_val = load i32, i32* %radius_ptr
  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([3 x i8], [3 x i8]* @str_fmt_i32, i32 0, i32 0), i32 %radius_val)

  ; Закриваємо Circle
  call i32 (i8*, ...) @printf(i8* getelementptr inbounds ([4 x i8], [4 x i8]* @str_close_br, i32 0, i32 0))

  ret void
}


Два варіанти організації коду (Оптимізація)
Inline Expansion (Вбудовування прямо у місці виклику):
Ви розгортаєте увесь цей код з printf безпосередньо туди, де написано print(c).
Плюси: Дуже просто реалізувати в генераторі коду.
Мінуси: Роздуває розмір підсумкового бінарника (Code bloat), якщо print(c) викликається у багатьох місцях.
Helper Function Generation (Генерація окремої функції під тип):
Для кожної структури T компілятор автоматично генерує допоміжну функцію void print_T(T* ptr).
При зустрічі print(c) компілятор просто генерує виклик call void @print_Circle(%Circle* %c).
Плюси: Компактний IR-код, чистота та перевикористання.

       Фаза 1: парсинг полів — зупиняється при fn або }.
       Фаза 2: парсинг member functions — зупиняється при }.
   - Додано метод parse_member_fn_decl(known_names) — парсить fn ident := (...) -> type { block }.
   - Перевіряє конфлікти імен між полями та методами.
   - parse_operand оновлено: після ident при зустрічі . і далі ident( — будує MemberCallNode
     (ланцюжок закінчується); при . + ident без ( — будує FieldAccessNode (ланцюжок продовжується).

   SemanticChecker (compiler.py):
   - visit_struct_def тепер перевіряє підписи та тіла кожного методу через _check_member_fn_body.
   - _check_member_fn_body: налаштовує область видимості з полями структури та параметрами методу.
   - visit_member_call: перевіряє тип ресивера, знаходить метод, перевіряє аргументи.
     Анотує node.mfn і node.type.

   CodeGenVisitor (compiler.py):
   - visit_struct_def оголошує IR-функції для кожного методу (self-pointer як перший аргумент)
     та генерує їхні тіла через _gen_member_fn_body.
   - _gen_member_fn_body: будує entry block, GEP-покажчики на поля через _field_ptrs,
     виділяє слоти для параметрів.
   - visit_member_call: отримує lvalue-покажчик ресивера, передає як перший аргумент виклику.
   - visit_var, get_lvalue_ptr, visit_assign оновлено для пошуку через _field_ptrs всередині методу.
