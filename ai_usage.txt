User prompt: Програма має зчитати три точки Point{x, y}, знайти точки, для яких x*x + y*y дорівнює введеному числу, надрукувати їх і вивести кількість збігів. У мові немає масивів, але є структури та функції з параметрами. Поясни простими словами, навіщо винести перевірку однієї точки в окрему функцію report(point, target), яка друкує збіг і повертає 1 або 0.
Response: Оскільки в мові немає масивів, ти не можеш скласти точки в один список і прогнати їх через цикл — доводиться обробляти кожну точку окремо (p1, p2, p3). Винесення перевірки у функцію report(point, target) вирішує одразу кілька проблем:
Прибирає копіпаст (замінює цикл). Без функції довелося б тричі писати ту саму перевірку if (x*x + y*y == target) і команду друку. Функція дозволяє описати цю логіку один раз, а далі просто викликати її по черзі для кожної точки.
Перетворює підрахунок на звичайне додавання. Повернення 1 (якщо точка підійшла) або 0 (якщо ні) — це хитрий прийом, щоб не заводити окремий лічильник із купою умов. Загальна кількість збігів рахується одним зрозумілим рядком:
total = report(p1, target) + report(p2, target) + report(p3, target)


Захищає від випадкових помилок. Коли формула написана лише в одному місці, ти не зробиш одруківку під час копіювання коду для другої чи третьої точки. А якщо умова задачі зміниться (наприклад, знадобиться знак < замість ==), виправити код доведеться лише в одному рядку.
Робить код охайним завдяки структурі. Замість того, щоб передавати у функцію по два окремі числа (x та y), ти передаєш одну цілісну «коробку» Point, і функція сама дістає з неї потрібні координати.
У результаті головна програма виходить максимально короткою і читається як звичайний текст: «зчитай три точки, перевір кожну через report і додай результати».

User prompt: У навчальній мові є структура Point з полями i32 x та i32 y, а також member function d2(), що повертає x*x + y*y. Поясни, чому обчислення квадрата відстані доцільно розмістити в методі самої структури, а не повторювати в основній програмі. Наведи короткий приклад псевдокоду.
Response: Розміщення обчислення всередині методу d2() прив'язує дію безпосередньо до даних, над якими вона виконується. У програмуванні це один із базових принципів організації коду, і на практиці він дає кілька переваг:
Зрозумілість замість формул. Умова p.d2() == target читається як готове твердження («квадрат відстані точки дорівнює заданому числу»), тоді як p.x * p.x + p.y * p.y == target змушує щоразу подумки розбирати математичний вираз.
Захист від одруківок. Коли доводиться багато разів писати p1.x * p1.x + p1.y * p1.y, легко випадково написати p1.x * p1.y або переплутати p1 та p2. Метод d2() гарантовано використовує координати саме тієї точки, для якої його викликали.
Єдине місце для змін. Якщо формулу знадобиться оновити (наприклад, перейти на i64 для захисту від переповнення при великих координатах), ти зміниш лише один рядок усередині структури, а не шукатимеш усі копії формули в основній програмі.
Логічна цілісність. Структура Point зберігає координати точки, тому цілком природно, що вона сама вміє обчислювати свої базові геометричні властивості.
struct Point {
    i32 x
    i32 y

    fn d2() -> i32 {
        return x * x + y * y
    }
}

fn report(Point p, i32 target) -> i32 {
    if p.d2() == target {
        print(p.x, p.y)
        return 1
    }
    return 0
}

fn main() {
    Point p1 = read_point()
    Point p2 = read_point()
    Point p3 = read_point()
    i32 target = read_i32()

    i32 count = report(p1, target) + report(p2, target) + report(p3, target)
    print(count)
}

User prompt: Я додаю extern fn name := (parameters) -> result у навчальну мову, де звичайні fn мають тіло. Які граматичні правила треба визначити для позиції extern-декларації, її тіла та заборони оголошувати її всередині блока чи після виконуваних інструкцій?
Response: Щоб забезпечити ці обмеження вже на етапі синтаксичного аналізу (парсингу), граматику потрібно стратифікувати — розділити нетермінали для оголошень верхнього рівня, блоків та виконуваних інструкцій, а також зафіксувати їхній суворий порядок.
1. Позиція на верхньому рівні та заборона після виконуваних інструкцій
Якщо в мові дозволені виконувані інструкції на верхньому рівні (поза функціями), кореневе правило Program має жорстко розділяти етап оголошень і етап виконання:
Program      ::= ExternDecl* TopLevelDecl* Stmt*
(* або, якщо extern може чергуватися зі звичайними fn та struct: *)
Program      ::= TopLevelDecl* Stmt*

TopLevelDecl ::= ExternFnDecl | FnDecl | StructDecl


Як це працює: Парсер зчитує TopLevelDecl у циклі доти, доки бачить ключові слова extern, fn або struct. Щойно зустрічається перша виконувана інструкція (Stmt), парсер переходить до розбору Stmt* і більше ніколи не повертається до оголошень. Будь-який extern після інструкції автоматично викличе синтаксичну помилку, оскільки в правилі Stmt цього ключового слова немає.
Якщо ви хочете, щоб extern-оголошення стояли навіть вище за звичайні функції, використовуйте перший варіант (ExternDecl* TopLevelDecl* Stmt*).
2. Відсутність тіла та термінатор декларації
Звичайна функція вимагає наявності блока { ... }, тоді як extern fn описує лише сигнатуру для зв'язування із зовнішнім кодом і не повинна мати тіла:
FnDecl       ::= 'fn' IDENT ':=' ParamList ('->' Type)? Block
ExternFnDecl ::= 'extern' 'fn' IDENT ':=' ExternParamList ('->' Type)? Term


Обов'язковий термінатор (Term): Правило ExternFnDecl має закінчуватися явним роздільником — крапкою з комою ; або перенесенням рядка NEWLINE (залежно від того, як у вашій мові завершуються інструкції). Без цього, якщо в мові існують анонімні блоки коду { ... } як інструкції (Stmt), виникне неоднозначність або плутанина, де наступний блок коду виглядатиме як тіло функції.
Параметри без імен (опціонально): Оскільки в extern fn немає тіла, де використовуються змінні-параметри, у ExternParamList зручно дозволити вказувати лише типи (наприклад, (i32, i32) -> i32), хоча підтримка імен (i32 x, i32 y) теж не завадить для документації коду.
3. Заборона оголошення всередині блока
Щоб extern fn не можна було написати всередині звичайної функції, умовного оператора if чи циклу, нетермінал Block має посилатися лише на виконувані інструкції та локальні змінні, повністю виключаючи TopLevelDecl:
Block     ::= '{' BlockItem* '}'
BlockItem ::= VarDecl | Stmt    (* ExternFnDecl та FnDecl тут відсутні *)


Оскільки нетермінал ExternFnDecl досяжний виключно з кореневого правила Program, а Block містить лише BlockItem (які, своєю чергою, можуть містити лише вкладені Block, IfStmt, WhileStmt тощо), граматика фізично унеможливлює появу extern усередині будь-яких фігурних дужок { ... }.
Для навчальної мови в рекурсивному парсері варто додати окрему перевірку: якщо під час розбору Block або Stmt* парсер зустрічає токен extern, замість загального "очікувалася інструкція" краще видати точне повідомлення про помилку — що зовнішні функції можна оголошувати лише на початку програми до виконуваного коду.

User prompt: Зовнішня C-функція викликається за символом лінкера, а компілятор знає лише її підпис. Чому варто дозволяти лише i32/i64 для параметрів і результатів, і які перевірки потрібні для bool, структур та конфліктів імен?
Response: Обмеження інтерфейсу зовнішніх функцій (FFI) лише типами i32 та i64 дозволяє підключити бібліотеки мови C без реалізації складних правил двійкового інтерфейсу (ABI) у вашому компіляторі.
Чому варто дозволяти лише i32 та i64
Тривіальна передача через регістри. У всіх популярних угодах про виклики (System V AMD64 ABI на Linux/macOS, Windows x64, ARM64) 32- та 64-бітні цілі числа передаються напряму через стандартні регістри загального призначення (rdi, rsi, rdx... або rcx, rdx...) і повертаються в eax/rax. Компілятору не потрібно генерувати приховані функції-обгортки — достатньо вивести звичайну інструкцію call.
Відсутність проблем із володінням пам'яттю. Рядки чи динамічні масиви в навчальних мовах зазвичай зберігаються як структура «вказівник + довжина» і не мають завершального нуль-байта (\0), якого очікує C. Робота лише з цілими числами позбавляє потреби робити автоматичне перетворення даних (маршалінг) і стежити за часом життя пам'яті.
Достатність для базового вводу/виводу. Цих двох типів вистачає, щоб реалізувати на боці C усі необхідні для навчальних задач примітиви: read_i32, print_i32, putchar, генерацію випадкових чисел чи роботу з таймером.
Які семантичні перевірки потрібні
Щоб програма не падала з неочевидними помилками на етапі лінкування або під час виконання, семантичний аналізатор має виконувати три групи перевірок для кожної декларації extern fn:
1. Заборона типу bool
У чому проблема: У мові C тип bool (_Bool) займає 1 байт, а стандарт вимагає, щоб на рівні бітів там зберігалося строго 0 або 1 (будь-яке інше значення в регістрі спричиняє Undefined Behavior). У вашій мові bool може займати ціле машинне слово або кодуватися як -1 для true. Також при поверненні bool із C-функції старші біти регістра rax можуть містити «сміття», яке зламає порівняння у вашому коді.
Що перевіряти: Під час перевірки типів відхиляйте bool як у списку параметрів, так і в типі результату extern fn. Користувач має явно передавати i32 (наприклад, конвертуючи умову в 0 або 1 у власному коді).
2. Заборона користувацьких структур (struct)
У чому проблема: Передача та повернення структур за значенням у C ABI — одна з найскладніших частин кодогенерації. Залежно від ОС та розміру структури, два поля i32 можуть пакуватися в один 64-бітний регістр, структура розміром понад 16 байтів вимагає передачі прихованого вказівника (sret) першим аргументом, а правила вирівнювання полів у пам'яті (padding) у вашій мові можуть не збігатися з правилами компілятора C.
Що перевіряти: Перевіряйте, що кожен параметр належить виключно до множини {i32, i64}, а тип результату — до {i32, i64, void} (або відсутній, якщо функція нічого не повертає). Будь-яка структура має викликати помилку компіляції.
3. Перевірка конфліктів імен у таблиці символів Оскільки extern fn звертається до символу лінкера напряму без декорування імен (name mangling), компілятор повинен гарантувати унікальність цього імені на рівні всієї програми:
Конфлікт із внутрішніми функціями (fn): Забороніть оголошувати extern fn foo та звичайну fn foo в одній програмі. Якщо компілятор не додає до внутрішніх функцій спеціальні префікси, лінкер зупиниться з помилкою multiple definition of 'foo'.
Дублювання extern fn: Забороніть повторне оголошення тієї самої зовнішньої функції. Особливо небезпечно, якщо друге оголошення має іншу кількість або типи параметрів — це призведе до читання випадкових даних із регістрів чи стека під час виклику.
Конфлікт зі структурами та глобальними змінними: Якщо у вашій мові єдиний простір імен або ім'я структури використовується як її конструктор (наприклад, Point(3, 4)), оголошення extern fn Point має блокуватися ще на етапі реєстрації глобальних символів.
Захист точки входу main: Оскільки ваш компілятор сам генерує функцію main для запуску програми, спробу оголосити extern fn main варто відхиляти одразу з повідомленням про зарезервоване ім'я.

User prompt: Внутрішні функції мого компілятора отримують LLVM-імена на кшталт f_name, а C-функція має зберегти початковий символ, наприклад abs. Як має відрізнятися LLVM declaration зовнішньої функції від визначення внутрішньої?
Response: У LLVM IR оголошення зовнішньої функції та визначення внутрішньої відрізняються ключовим словом, наявністю тіла та правилом формування глобального ідентифікатора (@name):
; Зовнішня C-функція (лише декларація для лінкера)
declare i32 @abs(i32)

; Внутрішня функція мови (повноцінне визначення з префіксом і тілом)
define i32 @f_square(i32 %x) {
entry:
  %res = mul i32 %x, %x
  ret i32 %res
}


Ключові відмінності між цими двома конструкціями:
Ключове слово declare замість define: declare вказує LLVM, що реалізація функції знаходиться зовні (у стандартній бібліотеці C або іншому .o-файлі) і її адресу має підставити лінкер. define створює нову функцію безпосередньо у вашому модулі.
Відсутність тіла та базових блоків: Після списку типів аргументів у declare немає фігурних дужок { ... }, міток на кшталт entry: чи інструкції ret. Спроба додати тіло до declare викличе помилку парсингу LLVM IR.
Оригінальне ім'я символу (@abs проти @f_...): Для extern fn кодогенератор не додає префікс f_, щоб символ у таблиці експорту/імпорту точно збігся з C-функцією. До речі, завдяки префіксу f_ у внутрішніх функцій, на рівні LLVM IR ваша власна функція fn abs (@f_abs) і зовнішня extern fn abs (@abs) навіть не конфліктуватимуть за іменем (хоча на рівні вашої мови такий конфлікт усе одно варто заборонити).
Відсутність імен параметрів у сигнатурі: У declare вказуються лише типи параметрів ((i32) або (i32, i64)), оскільки використовувати їх усередині тіла все одно ніде. У define параметрам зазвичай дають імена віртуальних регістрів ((i32 %x)).
Опціональна внутрішня лінковка (internal): Для внутрішніх функцій, які не викликаються з C, у визначення корисно додавати модифікатор define internal i32 @f_square(...). Це підказує оптимізатору LLVM, що функція не експортується назовні, і дозволяє агресивніше її інлайнити або видаляти, якщо вона не використовується. Для declare цей модифікатор не застосовується — зовнішня декларація завжди має external linkage за замовчуванням.
Обидва варіанти за замовчуванням використовують стандартну угоду про виклики мови C (ccc), тому в місці виклику інструкція call генерується однаково — достатньо зберігати готове LLVM-ім'я (@abs або @f_square) у записі функції в таблиці символів:
%1 = call i32 @abs(i32 -5)
%2 = call i32 @f_square(i32 %1)



User prompt: 1Оптимізатор видаляє невикликані функції та виклики без побічних ефектів, але тіло extern-функції йому невідоме. Як безпечно поводитися з викликами extern під час оптимізації, і які тести доведуть, що невикористана декларація видаляється, а виклик із побічним ефектом зберігається?
Response: Оскільки тіло extern-функції приховане в зовнішньому об'єктному файлі або бібліотеці, оптимізатор повинен застосовувати до неї консервативний (найгірший) сценарій: за замовчуванням будь-яка зовнішня функція вважається «нечистою» (такою, що змінює глобальний стан, виконує ввід/вивід або може завершити програму).
Як безпечно поводитися з extern під час оптимізації
Не видаляти виклики з невикористаним результатом (DCE): Для внутрішньої функції компілятор може проаналізувати її тіло і довести, що вона чиста (не пише в пам'ять і не викликає нечистих функцій), а отже, її невикористаний виклик можна прибрати. Для extern fn так робити заборонено: навіть якщо повернене значення ігнорується, інструкція call має залишитися.
Не згортати дублікати (CSE) та не змінювати порядок: Вираз f() + f() для зовнішньої функції не можна оптимізувати до 2 * f(), а два послідовні виклики extern-функцій не можна переставляти місцями, оскільки вони можуть залежати від спільного стану (наприклад, буфера виводу чи генератора випадкових чисел).
Видаляти самі декларації за підрахунком посилань: Хоча живий виклик видаляти не можна, саму декларацію declare ... варто прибирати з фінального LLVM IR, якщо в програмі немає жодного реального виклику цієї функції (або всі виклики зникли після видалення недосяжного коду, наприклад гілки if (false)).
Покладатися на правила атрибутів LLVM: Якщо під час генерації LLVM IR ви не додаєте до declare атрибути чистоти на кшталт memory(none) чи willreturn, оптимізатор самого LLVM також вважатиме функцію такою, що має побічні ефекти, і не видалить її виклик на етапі власних проходів.
Тести для перевірки оптимізатора
Щоб надійно перевірити обидві поведінки, достатньо двох наскрізних тестів (які перевіряють і згенерований .ll-файл, і реальну роботу скомпільованої програми):
1. Видалення невикористаної декларації (перевірка через неіснуючий символ) Оголосіть у програмі зовнішню функцію, якої фізично немає в стандартній бібліотеці C, але ніде її не викликайте (або викличте лише всередині завідомо мертвої гілки):
extern fn ghost_missing_symbol() -> i32

fn main() -> i32 {
    if 0 == 1 {
        ghost_missing_symbol()
    }
    return 0
}


Що перевіряє тест:
У згенерованому LLVM IR після оптимізації відсутній рядок declare i32 @ghost_missing_symbol().
Компіляція та лінкування завершуються успішно. Якби оптимізатор не видалив невикористану декларацію, лінкер зупинився б із помилкою undefined reference to 'ghost_missing_symbol' (або залишив би зайвий імпорт у бінарному файлі).
2. Збереження виклику з побічним ефектом при ігноруванні результату Використайте стандартну функцію putchar із libc (вона приймає код символу i32 і повертає i32, але нас цікавить саме її побічний ефект — друк у консоль):
extern fn putchar(i32 ch) -> i32

fn main() -> i32 {
    putchar(65)   // код літери 'A', результат повернення ігнорується
    putchar(66)   // код літери 'B'
    return 0
}


Що перевіряє тест:
У фінальному LLVM IR усередині @main збереглися обидві інструкції call i32 @putchar(i32 65) та call i32 @putchar(i32 66) у правильному порядку (оптимізатор не викинув їх через невикористане значення і не згорнув через CSE).
Під час запуску скомпільований файл виводить у stdout рядок AB.
