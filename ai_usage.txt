User prompt: а чому в оптимізованому варіанту немає виділення та збереження 0, там лише рядок для поверення нуля
Response: У коді без оптимізації (-O0) компілятор створив комірку %1 для повернення значення та виконав store i32 0, ptr %1. Однак при оптимізації (-O1) ця комірка і запис зникають з трьох основних причин:
Значення повертається як безпосередня константа (Immediate Constant): Інструкція ret i32 0 в LLVM IR здатна повертати значення константи напряму. Компілятору не потрібна проміжна змінна на стеку, щоб повернути фіксоване число 0 — це число вбудовується безпосередньо в машиний код.
Видалення мертвого запису (Dead Store Elimination — DSE): Оптимізатор аналізує використання пам'яті: інструкція store i32 0, ptr %1 записує 0 у комірку %1, але надалі в функції немає жодної інструкції load, яка б зчитувала значення з %1. Оскільки цей запис ніхто не бачить і ніде не використовує, він вважається «мертвим кодом» і просто видаляється.
Видалення невикористаного alloca (Dead Code Elimination — DCE): Після видалення інструкції store, на виділену пам'ять %1 = alloca i32 більше не посилається жодна інструкція в програмі. Непотрібна виділена пам'ять на стеку видаляється повністю.
Завдяки as-if rule (правилу збереження зовнішньої поведінки) компілятор гарантує, що прибрана пам'ять та інструкції запису ніяк не змінюють результат виконання — програма однаково завершується з кодом 0, але працює швидше й не витрачає стек.

User prompt: я не зовсім розумію в чому різниця між return 0 в цих двох випадках, адже що там що там записана константа в return? то чому в одному випадку виділяється окремо памʼять під цю константу а в іншому ні
Response: Різниця полягає не в самій константі, а в підході компілятора до побудови коду на різних рівнях оптимізації:
1. Режим без оптимізації (-O0): "Механічний переклад"
На рівні -O0 Clang працює за жорстким шаблоном і свідомо не намагається аналізувати, чи потрібен код:
Шаблон для функцій: Коли компілятор бачить функцію, що повертає значення, він автоматично виділяє комірку пам'яті на стеку (%1 = alloca i32) для збереження результату (це стандартне правило для return).
Шаблон для return 0;: Бачачи рядок return 0;, компілятор просто механічно записує значення 0 у цю виділену комірку (store i32 0, ptr %1).
Компілятор при -O0 не перевіряє, чи буде хтось надалі зчитувати цю комірку. Його завдання на -O0 — максимально буквально й без роздумів перекласти AST у LLVM IR, щоб відлагоджувач (debugger) бачив кожну змінну і кожну дію.
2. Режим з оптимізацією (-O1): "Аналіз та чистка"
При включенні оптимізації в гру вступають проходи аналізу LLVM (такі як Dead Code Elimination / SROA):
Оптимізатор дивиться на згенерований IR i ставить аналітичні запитання:
"Ми записали 0 у комірку %1. Чи є далі в коді хоч одна інструкція load, яка зчитує значення з %1?" → Ні, немає.
"Чи викликає цей store якийсь зовнішній побічний ефект?" → Ні, це локальний стек.
Оскільки запис у пам'ять виявився «мертвим» (його результат нікому не потрібен), оптимізатор видаляє і store, і сам alloca.
Залишається лише мінімально необхідна дія — безпосередньо повернути число: ret i32 0.
Коротке резюме
Пам'ять у режимі -O0 виділяється не тому, що вона потрібна для повернення нуля, а тому що компілятор у режимі без оптимізацій сліпо дотримується шаблону генерації коду й ще не знає, що ця пам'ять виявиться непотрібною. Режим -O1 просто видаляє цей зайвий шаблонний код.

User prompt: то цей оптимізатор також оптимізує сам вже assambly код? не лише вхідний текст коду нашої вигаданох мови?
Response: У реальних компіляторах (як Clang/LLVM) оптимізації відбуваються на кількох рівнях послідовно, але у вашій практичній роботі завдання сформульоване конкретніше.
Як це працює взагалі (на прикладі Clang/LLVM)
Оптимізатор дійсно працює не лише з вхідним текстом, а з кількома внутрішніми представленнями коду:
High-level (AST): Оптимізації на рівні синтаксичного дерева мови.
Intermediate Representation (LLVM IR): Саме на цьому рівні працював приклад із clang -O1. Внутрішній оптимізатор LLVM (opt) отримує Intermediate Representation (проміжний код) і проводить проходи на кшталт DCE (видалення мертвого коду) чи mem2reg (перенесення змінних зі стеку в регістри).
Low-level (Ассемблер / Машинний код): Бекед компілятора оптимізує вже безпосередньо ассемблерний код під конкретний процесор (оптимізація використання регістрів, переупорядкування інструкцій тощо).

User prompt: поясни ці два контексти в яких виконується оптимізація:  dce (drop an instruction without side effects whose result is unused) and globaldce (drop an internal function nobody references що це таке
Response: Обидва ці терміни описують проходи оптимізації видалення «мертвого» (непотрібного) коду на рівні LLVM IR (Intermediate Representation), але вони працюють у різних контекстах і на різних рівнях деталізації.
1. dce (Dead Code Elimination — локальне видалення)
Контекст/Рівень: Працює всередині однієї функції на рівні окремих дрібних інструкцій (мікрорівень).
Сутність: Видаляє інструкцію, якщо її обчислений результат надалі ніде не використовується і якщо вона не має побічних ефектів (side effects).
Що таке побічний ефект: Це дія, яка змінює стан зовнішнього світу або пам'яті — наприклад, вивід тексту на екран (print), зчитування даних (read), або запис у глобальну змінну. Інструкцію з побічним ефектом видаляти не можна, навіть якщо її повернене значення нікому не потрібне.
Приклад: Якщо в IR є інструкція %sum = add i32 %a, %b, але значення %sum далі жодного разу не передається в інші інструкції чи в ret, прохід dce її стирає.
2. globaldce (Global Dead Code Elimination — глобальне видалення)
Контекст/Рівень: Працює на рівні всього модуля / усієї програми (макрорівень).
Сутність: Аналізує граф викликів всієї програми і видаляє цілі функції (або глобальні змінні), на які немає жодного посилання чи виклику з точок входу (наприклад, з main).
Приклад: Якщо ви оголосили внутрішню функцію fn helper() { ... }, але ні main, ні будь-яка інша функція її не викликає, globaldce повністю вирізає цю функцію разом з усім її вмістом.

2. Пояснення речення про y та x
«If y is initialised from x and nobody reads y, then x is read only by a declaration that is about to disappear»
Розглянемо приклад з методички:
i32 x{10}
i32 y{x}
// далі в коді змінна y ніде не використовується


Коло 1:
Підраховуються читання: y має 0 читань, а x має 1 читання (бо його ім'я вказане в ініціалізаторі y{x}).
Декларація y видаляється, бо у неї 0 читань.
Зміст речення: Змінна x мала читання тільки всередині декларації y, яка саме зараз зникає («is about to disappear»).
Коло 2:
Разом із y зник і вираз y{x}.
Під час повторного обходу дерево вже не містить виразу y{x}, тому в x кількість читань стає 0.
На цьому колі видаляється і сама змінна x.
3. Уточнення щодо «видалення класів» та «дерева наслідування»
У завданнях практики взагалі НЕ йдеться про видалення ООП-класів чи дерева наслідування.
Плутанина виникає через використання слова class у прикладі коду:
class UseCounter: у методичці — це не частина програми, яку компілюють, а клас мовою Python у коді вашого компілятора (реалізація паттерна Visitor для обходу дерева).
Що насправді видаляється: Видаляються конкретні вузли оголошення окремих змінних (DeclNode) та глобальних функцій, які ніхто не читає й не викликає.
Яке це дерево: Дерево тут — це AST (Abstract Syntax Tree / Абстрактне синтаксичне дерево) всієї вашої програми, а не дерево наслідування об'єктів.
Приклад в AST-дереві:
Якщо у вашому коді є три змінні:
Block
 ├── Decl: x = 10
 ├── Decl: y = x
 └── Decl: z = 15  (використовується в exit z)


Видалення не чіпає весь блок чи інші змінні. Воно видаляє лише один конкретний вузол Decl: y.
Вузол Decl: z та інші частини дерева залишаються повністю недоторканими, оскільки z читається в exit.

1. Головна функція проходу (remove_unused)
def remove_unused(tree):
    while True:
        # Крок 1: Обхід дерева та підрахунок вживань
        counter = UseCounter()
        tree.accept(counter)
        
        # Крок 2: Відбір вузлів з 0 читань/викликів за унікальним id(node)
        dead_ids = {node_id for node_id, count in counter.reads.items() if count == 0}[cite: 3]
        
        # Якщо за це коло нічого не знайдено — нерухома точка (фікспойнт) досягнута
        if not dead_ids:
            return tree[cite: 3]
            
        # Крок 3: Видалення мертвих вузлів і створення нового дерева
        pruner = Pruner(dead_ids)
        tree = pruner.prune(tree)[cite: 3]


2. Візитор підрахунку читань (UseCounter)
class UseCounter:
    def __init__(self):
        # Словник: id(DeclNode/FnNode) -> кількість читань/викликів
        self.reads = {}[cite: 3]

    def read(self, decl_node):
        key = id(decl_node)[cite: 3]
        self.reads[key] = self.reads.get(key, 0) + 1[cite: 3]

    def visit_decl(self, node):
        # Кожна оголошена змінна реєструється зі стартовим значенням 0
        self.reads.setdefault(id(node), 0)[cite: 3]
        
        # Безпека: якщо ініціалізація має виклик функції або read(), змінну видаляти заборонено
        if any(has_call_or_read(expr) for expr in node.inits):[cite: 3]
            self.read(node)[cite: 3]
            
        # Обходимо вирази ініціалізації для пошуку інших змінних
        for expr in node.inits:
            expr.accept(self)[cite: 3]

    def visit_var(self, node):
        # node.decl встановлений Checker-ом і вказує на конкретний DeclNode
        self.read(node.decl)[cite: 3]

    def visit_assign(self, node):
        # Ліва частина y := 5 НЕ рахується за читання y
        # Але якщо справа є виклик функції — зберігаємо змінну
        if has_call_or_read(node.value):[cite: 3]
            self.read(node.decl)[cite: 3]
            
        node.value.accept(self)[cite: 3]

    def visit_call(self, node):
        # Task 2: підраховуємо виклики для глобальних функцій
        if node.is_global_fn:
            self.read(node.fn_decl)[cite: 3, 4]
            
        for arg in node.args:
            arg.accept(self)


3. Візитор видалення вузлів (Pruner)
class Pruner:
    def __init__(self, dead_ids):
        self.dead_ids = dead_ids[cite: 3]

    def visit_block(self, node):
        new_statements = []
        
        for stmt in node.statements:
            # 1. Пропускаємо невикористану декларацію змінної
            if isinstance(stmt, DeclNode) and id(stmt) in self.dead_ids:[cite: 3]
                continue
                
            # 2. Пропускаємо присвоєння змінній, чию декларацію видалено
            if isinstance(stmt, AssignNode) and id(stmt.decl) in self.dead_ids:[cite: 3]
                continue
                
            # 3. Рекурсивно обходимо вкладені блоки (if, while)
            stmt.accept(self)
            new_statements.append(stmt)
            
        # Замінюємо список операторів новим (відфільтрованим)
        node.statements = new_statements[cite: 3]

    def visit_program(self, node):
        # Task 2: видалення функцій з 0 викликами на верхньому рівні
        node.functions = [
            fn for fn in node.functions 
            if id(fn) not in self.dead_ids
        ][cite: 3, 4]
        
        for fn in node.functions:
            fn.accept(self)

Response: У додатковому завданні (Additional task: Calls without effects) правило збереження змінних уточнюється: виклик функції або методу зберігається лише в тому випадку, якщо він має побічний ефект (observable effect).
1. Що вважається ефектом (Base Effects)
Функція або вираз має побічний ефект, якщо виконується хоча б одна з базових умов:
Введення / виведення: Тіло містить виклик print або read().
Мутація: Це мутуючий метод (mutating member function), який змінює стан об'єкта, на якому його викликано.
Потенційне незавершення: Тіло містить цикл while або прямо/опосередковано викликає саме себе (рекурсія).
Виклик іншої функції з ефектом: Функція викликає будь-яку іншу функцію чи метод, що вже має ефект.
2. Як поширювати ефекти між функціями (Fixpoint / Нерухома точка)
Оскільки функції можуть викликати одна одну (зокрема циклами), обчислення множини функцій із ефектами виконується через пошук нерухомої точки (fixpoint algorithm):
Ініціалізація: Зібрати початкову множину Effects, додавши туди всі функції та методи, які мають прямі базові ефекти (print, read(), while, рекурсію або мутацію).
Ітерація поширення: Пройтися по всіх функціях програми. Якщо функція A містить виклик функції B, і B вже є у множині Effects, то A також додається до Effects.
Критерій зупинки: Повторювати ітерації поширення в циклі доти, доки за чергове коло до множини Effects не буде додано жодної нової функції.
3. Робота з окремими випадками
Мутація (Mutating Member Functions):
Виклик мутуючого методу завжди вважається ефектом і зберігається, навіть якщо його повернене значення ніде не використовується.
Приклад: у i32 t{c.bump()} виклик bump() змінює лічильник всередині c. Змінну t видаляти заборонено, бо це змінить стан c.
Натомість виклик константного методу-переглядача без мутацій (наприклад, i32 u{c.peek()}) не має ефекту і буде видалений, якщо u ніхто не читає.
Цикли (while) та Рекурсія:
Наявність циклу while або рекурсивного виклику означає, що функція потенційно може зациклитися й не повернути управління.
Зависання програми є зовнішньо спостережуваною поведінкою (observable behavior), тому такі функції завжди маркуються як ефект і не видаляються.
Виклики методів, Лямбд та Callable-об'єктів:
Виклик об'єкта або лямбди c(5) трактується як виклик відповідної функції/лямбди. Якщо тіло лямбди містить ефект (наприклад, print), сам виклик цієї лямбди стає ефектом і зберігає змінну.

Фактичне зіставлення відповідей Gemini з реалізацією Task 1, Task 2 та Additional Task

Примітка: нижче «взято» означає, що рекомендація Gemini справді відображена в коді або тестах.
«Не взято» позначає запропонований підхід або приклад, якого немає в реалізації; це не означає,
що він був окремо відхилений у дискусії.

11. Task 1 — підрахунок використань і повторне видалення:
Запити Gemini були про проходження по AST, підрахунок читань по декларації, видалення присвоєнь
та повторення, якщо перше видалення зробило інше значення невикористаним.
Взято:
- Лічильник читає посилання `VarNode.decl`, а не зіставляє імена. Це дозволяє розрізняти
  однойменні декларації в різних scope; приклад затінення перевіряє
  `tests/opt/02_shadowing.txt` та його точний знімок `tests/opt/02_shadowing.astc`.
- Декларації з нульовими читаннями та присвоєння до них видаляються з top-level і вкладених
  блоків, у функціях, методах і тілах lambda. Після змін лічильник запускається повторно.
  Каскадний приклад `x -> y -> z` є в `tests/opt/01_iteration.txt`.
- Параметри, поля struct, lambda та member functions не видаляються; умова `if`/`while`
  зберігається, навіть коли її тіло спорожніло.
Не взято:
- Замість окремого тесту з кожним запропонованим Gemini прикладом використано наявні
  та нові тести `tests/opt`; їхні повні очікувані дерева зафіксовано у `.astc`.

12. Task 2 — невикористані глобальні функції:
Взято:
- Підраховуються виклики global functions у top-level statements, інших global functions,
  member functions та lambda bodies; видаляються тільки глобальні декларації функцій.
- Видалення повторюється, тому після вилучення `unused` видаляється `helper`, а функція,
  на яку є виклик з живого коду, залишається. Це перевіряє
  `tests/opt/07_unused_functions.txt`.
- Взаємно рекурсивні функції зберігаються: кожна має виклик, тож звичайний підрахунок не
  видаляє цикл. Взаємні виклики `first`/`second` разом із функцією з `while` перевіряються в
  `tests/opt/12_nonreturning_calls.txt`.
Не взято:
- Не видаляються функції лише тому, що їхній виклик граф утворює цикл; reachability від entry
  point або LLVM `globaldce` замість tree-проходу не реалізовані.

13. Additional Task — виклики без ефектів:
Запити Gemini описували базові ефекти, поширення ефектів до нерухомої точки, мутації,
цикли, рекурсію, виклики через member functions і lambda.
Взято:
- Функції та методи з `print`, `read`, `while` або мутацією позначаються effectful.
  Рекурсивний цикл в call graph теж є ефектом; позначка поширюється на функції, які
  викликають effectful-функції.
- Не використаний результат чистого виклику більше не тримає декларацію; чистий standalone
  function-call statement також видаляється. `read()` і виклик з ефектом лишаються.
- Mutating method лишається, а чистий accessor можна видалити, що перевіряє
  `tests/opt/10_mutating_call.txt`. Ефект, що передається через виклики, перевіряє
  `tests/opt/11_effect_chain.txt`; loops і взаємна рекурсія — `tests/opt/12_nonreturning_calls.txt`;
  lambda з ефектом і чиста lambda — `tests/opt/13_lambda_effects.txt`.
Не взято / обмеження:
- Ефект вважається на рівні цілої функції: якщо тіло містить `while`, воно effectful
  незалежно від того, чи доводиться, що цикл завершиться. Аналіз не виконує path-sensitive
  доведення умов циклів.
- Початковий варіант із додатковим `quiet(9)` залишився окремим тестом
  `tests/opt/09_pure_calls.txt`; програму з прикладу Gemini також додано окремо як
  `tests/opt/15_pure_calls_example.txt`.
- Фактичний результат кожного тесту зафіксований у `.expected` та повному `.astc`.

14. Тести, CLI та примітка про пам'ять:
Взято:
- На вимогу практичної всі 15 `tests/opt/*.txt` мають `.expected` і повний `.astc`;
  тест-ранер перевіряє точний вивід AST, а не лише наявність окремих рядків.
- Прапорець `--remove-unused` можна ставити до, між або після positional paths;
  тестується через `argparse.parse_intermixed_args()`.
- `OPT=0` запускає `tests/ok` і `tests/err` без оптимізації, `OPT=1` — лише з нею,
  а стандартне `OPT=both` перевіряє обидва режими. Каталог `tests/opt` в усіх режимах
  порівнює оптимізоване та базове виконання.
- README пояснює CPython references, відсутність parent pointers і результат перевірки
  `weakref` після від'єднання декларації та звільнення semantic checker. Скрипт
  `tests/test_ast_reclamation.py` перевіряє, що reference стає `None` без `gc.collect()`.
Не взято:
- Додатковий окремий інструмент на кшталт sanitizer не використовувався: для Python
  виконано саме weak-reference перевірку, запропоновану практичною.
