1. Як правильно записати type
У формальній граматиці (EBNF) парсер на етапі синтаксичного аналізу ще не знає, які саме структури були оголошені — для нього ім'я будь-якої структури це просто ідентифікатор (ident).
Тому тип записується так:
type ::= "i32" | "i64" | "bool" | ident


Якщо хочеться зробити граматику більш наочною та семантично виразною:
primitive_type ::= "i32" | "i64" | "bool"

type           ::= primitive_type | struct_type

2. Уточнення правила для struct

struct_def ::= "struct" ident NL "{" NL { field_decl } "}" NL
field_decl ::= type [ "mut" ] ident NL


Або в один суцільний запис:
struct_def ::= "struct" ident NL "{" NL { type [ "mut" ] ident NL } "}" NL

class SemanticChecker:
    def __init__(self):
        self.scopes = [{}]
        self.structs = {}  # struct_name -> StructInfo

    def visit_struct_def(self, node):
        if node.name in self.structs or node.name in ("i32", "i64", "bool"):
            self._sem_err(node.line, node.col, f"type '{node.name}' is already defined")

        fields = {}
        for idx, field_ast in enumerate(node.fields):
            # Перевірка, чи тип поля існує (примітивний або вже оголошена структура)
            if field_ast.type_name not in ("i32", "i64", "bool") and field_ast.type_name not in self.structs:
                self._sem_err(field_ast.line, field_ast.col, f"unknown type '{field_ast.type_name}'")

            # Перевірка на дублікати полів у структурі
            if field_ast.name in fields:
                self._sem_err(field_ast.line, field_ast.col, f"duplicate field '{field_ast.name}' in struct '{node.name}'")

            fields[field_ast.name] = FieldInfo(
                name=field_ast.name,
                type_name=field_ast.type_name,
                mutable=field_ast.mutable,
                index=idx
            )

        self.structs[node.name] = StructInfo(node.name, fields)

    # 4. Локальні символи функції
    old_symbols = self.symbols
    self.symbols = {}

    for i, arg in enumerate(func.args):
        p_node = node.params[i]
        arg.name = p_node.name
        ptr = self.builder.alloca(arg.type, name=p_node.name)
        self.builder.store(arg, ptr)
        self.symbols[p_node.name] = ptr

    # 5. Генерація тіла функції
    node.body_block.accept(self)

    # 6. Відновлюємо попередній контекст builder/symbols
    self.symbols = old_symbols
    self.builder = prev_builder



User prompt: яка команда використовується для ребейзу гільки на кінець іншої гілки
Response: Основна команда:
git rebase <назва_цільової_гілки>


Якщо ви зараз перебуваєте на своїй гілці (наприклад, feature) і хочете перенести її коміти поверх останніх змін із гілки main:
git checkout feature
git rebase main


Або виконати це однією командою з будь-якого місця:
git rebase main feature


(де main — гілка, на кінець якої ви стаєте, а feature — ваша поточна гілка)

User prompt: чому в гіт хабі може таке писати?  Can’t automatically merge. Don’t worry, you can still create the pull request.
Response: Це повідомлення означає, що між вашою гілкою та гілкою, куди ви робите Pull Request (наприклад, main), виникли конфлікти злиття (merge conflicts).
Чому це відбувається?
Git не може автоматично об'єднати код, тому що:
В обох гілках змінювали одні й ті самі рядки у файлах після того, як ваші гілки розійтися.
В одній гілці файл видалили, а в іншій — відредагували.
Оскільки Git не знає, які саме зміни є правильними, він залишає це рішення за вами.
Як це виправити?
Ви можете створити Pull Request далі (як і радить GitHub), а потім вирішити конфлікти одним із двох способів:
Спосіб 1: Через веб-інтерфейс GitHub (найпростіший)
Натисніть Create pull request.
У самому PR знизу з'явиться сіра кнопка Resolve conflicts.
Натисніть її, відредагуйте конфліктні файли (видаліть маркери <<<<<<<, =======, >>>>>>>) та збережіть рішення кнопкою Mark as resolved → Commit merge.
Спосіб 2: Локально через термінал (надійніший)
Підтягніть зміни з цільової гілки у свою локальну гілку (через merge або rebase), розв'яжіть конфлікти в редакторі коду та залиште новий комміт:
Варіант через merge:
git checkout ваша_гілка
git fetch origin
git merge origin/main
# (IDE покаже конфліктні файли — виправте їх)
git add .
git commit -m "Fix merge conflicts"
git push origin ваша_гілка


Варіант через rebase (якщо хочете чисту історію):
git checkout ваша_гілка
git fetch origin
git rebase origin/main
# (виправте конфлікти у файлах)
git add .
git rebase --continue
git push --force-with-lease origin ваша_гілка


Після того, как ви виправите конфлікти та відправите код на GitHub, кнопка Merge pull request стане зеленою та активною.
